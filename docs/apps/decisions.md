# Decision records

Condensed rationale for choices in `src/` that a future maintainer would
otherwise have to re-derive. Source files carry only the constraints the code
itself cannot show; the reasoning lives here. Task numbers, ruling ids and
review history are deliberately absent — `git log` has them.

## Census methodology

`docs/token-census.md` is generated by `scripts/census.ts` from mr-board's
`src/style.css`. It is the evidence base for every "this value is mr-board's,
verbatim" claim in the kit: section (a) is the `:root` / `:root.dark` variable
literals that became `tokens.colors`, section (b) is every rem/px
padding-margin-gap literal appearing at least twice in the board's `.tui-*`
rules (which became the `spacing` / `fontSize` ladders), section (c) is every
distinct `color-mix()` expression (which became the `surface.wash-*` semantic
tokens). Regenerate with `bun run census` when the board's stylesheet moves.

Two naming consequences of that ladder design, both load-bearing:

- A t-shirt rung carries the dominant rhythm and `remNN` / `pxN` rungs carry
  the exact remaining literals, so recipe CSS can reference a token for *any*
  real board value rather than half of them.
- Scale keys never start with a digit. `getSize()` treats a digit-leading token
  key as raw CSS, so `spacing["2xs"]` would emit the literal string `2xs` from
  a style prop instead of `var(--spacing-2xs)`. This is why the ladder reads
  `xxs`/`xxl` rather than `2xs`/`2xl`.

## Chip: `as="button"`, not an `asButton` boolean

The brief floated `asButton?: boolean`; the recipe ships the builder's own
polymorphism instead. `as` is soribashi's one public polymorphism surface, and
a boolean that silently means `as="button"` is a second, undocumented one the
two can then disagree about (`<Chip asButton as="a">`). `as` also carries the
target element's types with it, so `<Chip as="button" disabled type="submit">`
type-checks while `<Chip disabled />` does not — with a boolean the prop surface
stays typed as span attributes while a button renders, and every button-only
prop needs a cast at the call site. It composes for free where a boolean
vocabulary would need a second `asLink` (mr-board already wraps one chip in an
`<a>`). And `as` resolves *after* `useProps`, so
`Chip.extend({ defaultProps: { as: 'button' } })` retargets the element from a
theme. The one thing the boolean would have bought — a call site that reads as
a flag — is bought instead by the CSS keying interactive treatment on
`:is(button, a)`, so element and styling cannot disagree.

## StatusDot: dot tokens bypass the intent resolver

`STATUSDOT_TONES` maps `intent` straight to `--dot-ok`/`--dot-warn`/`--dot-bad`
rather than going through `autoVars` and `tuiIntentResolver`. The resolver maps
`ok -> green`, which would land an `intent="ok"` dot on `--color-green-500` —
mr-board's ordinary text green, the same hue every other `intent="ok"` control
uses. The dot family is deliberately a separate, more saturated palette: a
status dot has to read at a glance across a wall of rows, so it gets its own
visibility budget. Routing it through the resolver would silently collapse that
distinction.

The same reasoning is why StatusDot declares no `vocabularyAxes`: opting
`intent` in would validate call sites against the theme's full seven-value
vocabulary *and* route colour through `autoVars`, the two things this recipe
must not do. `intent` here is a three-value recipe-local scalar that happens to
share a name with the theme axis.

## Per-recipe `box-sizing: border-box`

Five recipes (Modal, SideDrawer, Panel's collapsed bar, StatusDot's tooltip,
ToastHost's toast, ContextMenu's root and item) declare `box-sizing:
border-box` on a box whose `width`/`max-width` mr-board has always treated as
an outer measure. mr-board gets that from a global `* { box-sizing: border-box }`
reset; the kit's copy of that reset lives in `src/canvas.css`, which is
explicitly optional ("components do not require it"). Without the per-recipe
declaration, a consumer who skips the canvas gets a "420px" modal measuring
~455px, a "320px" left drawer measuring 349px, and so on.

What it does and does not guarantee — it sits inside `@layer soribashi.recipes`,
and an unlayered author rule beats any layered one:

- consumer with no box-sizing opinion → border-box, correct (the case this
  closes, and the case the kit's own browser-tier tests run in);
- consumer whose reset is border-box → agrees, nothing changes (this is
  mr-board, so parity holds by agreement rather than by this rule winning);
- consumer with an unlayered `content-box` reset → their rule still wins.

The third case is a consumer deliberately overriding the kit and is out of
scope.

## Keyframes live outside the CSS module

Every `@keyframes` block, together with the `animation` / `animation-name`
declaration that names it (and any `prefers-reduced-motion` override of that
declaration), lives in a plain `<Recipe>.keyframes.css` sibling of the
recipe's `.module.css`, still inside `@layer soribashi.recipes`, selected by
the recipe's public `data-part`, and side-effect-imported from the recipe
TSX. Five recipes carry one: Spinner (`sb-spinner-spin`), Chip
(`chip-pulse`), Drawer (`drawer-slide-in`), ContextMenu (`contextmenu-in`),
ToastHost (`toasthost-in`).

Two bundlers disagree about a keyframe inside a CSS module, in opposite
directions, and no single-file layout satisfies both:

- Bun through 1.3.14 hashes the `@keyframes` ident but emits `animation` /
  `animation-name` verbatim (oven-sh/bun#18921). In a `Bun.build` consumer
  the ring painted its first frame and never moved: `animation:
  sb-spinner-spin` next to `@keyframes sb-spinner-spin_UXKcrg`. The upstream
  fix is not in a released Bun that consumers pin, and the kit has to animate
  on the ones that still have the bug.
- Vite hashes the `animation` ident whether or not the module declares that
  keyframe. Moving only the `@keyframes` out would have frozen the workshop
  and the browser test tier instead.

`:global()` is not an escape hatch: `@keyframes :global(name)` is a parse
error in Bun.

Consequences a later change must keep:

- The idents are global now, so their uniqueness is the collision avoidance
  (ContextMenu's `contextmenu-in` rather than mr-board's `tui-menu-in`). The
  hash never protected them in Bun, and no longer exists to protect them
  anywhere.
- The `[data-part]` rule applies even under `unstyled`, which suppresses the
  module class but still stamps the part. An `unstyled` Spinner still spins;
  an `unstyled` Chip with `pulse` still pulses. Nothing in the kit relies on
  `unstyled` silencing motion.
- `scripts/copy-recipe-css.ts` ships `*.keyframes.css` next to
  `*.module.css`, `scripts/derive.ts` scrapes both for `tokenDependencies`,
  and `test/no-hardcoded-values.test.ts` sweeps both with the same rules and
  rejects any `@keyframes` / `animation` that reappears inside a module.
- `test/bun-build-keyframes.test.ts` bundles the barrel with the local `bun`
  and reads the emitted CSS; the browser tiers assert the computed
  `animationName` matches a real `CSSKeyframesRule` (`test/keyframes.ts`).
  Computed styles and `animationName !== "none"` alone cannot see this bug,
  and the visual tiers freeze motion on purpose.

Do not fold the two halves back into the module "to keep the recipe in one
file". That is the layout that froze deck.

## Why `src/provider.ts` exists

Bundlers key module identity by *resolved path*. Before this file, an adopter
imported `registerTheme` / `SoribashiProvider` from `@soribashi/core` directly.
From the adopter's own source that resolved through the adopter's
`node_modules`; from a file inside the kit, the adopter's leaf symlink was
realpathed to the kit's checkout first, so `@soribashi/*` resolved from
`tui-kit/node_modules/`. Same package, same version, byte-identical files — two
paths, therefore two module records: two `SoribashiContext` objects, two
vocabulary registries, two `createTheme` implementations. `registerTheme()`
wrote one registry while recipes read the other, so a recipe's `useTheme()`
found no Provider above it and silently fell back to the *default* theme,
emitting token refs the real theme never defines. No error, no warning; just
wrong colours. (Measured on mr-board's bundle: 2× `provider/context.ts`, 2×
`vocabulary-registry.ts`, 2× `create-theme.ts`.)

Re-exporting them from the kit collapses that to one identity by construction,
and an adopter needs no `@soribashi/*` dependency at all. The subpath exists
alongside the barrel re-export because an app entry usually wants only the
wiring, and the barrel drags every recipe's module graph — and every
`.module.css` — with it.

## `defineComponent` over `defineCompound` for the overlays

Modal and SideDrawer are category-2 transient overlays, which the authoring
skill pairs with `defineCompound`. They use `defineComponent` anyway. The
pairing exists because in soribashi a transient overlay wraps Base UI parts
whose open/close lifecycle Base UI owns; this kit has no `@base-ui/react`
dependency and none planned, the markup is mr-board's own, and the lifecycle is
the caller's `{open && <Modal/>}` conditional plus `useEscapeClose` /
`useBodyScrollLock`. The real test for a compound is composability, not slot
count — nobody imports a `Modal.Overlay` or a `SideDrawer.Panel`, and inventing
one would be an API promotion rather than a port.

ContextMenu is the kit's one genuine compound and earns it: mr-board's RowMenu
builds its item list conditionally, so the *consumer* decides what parts exist
and in what order. Two consequences apply there and nowhere else in the kit —
`defineCompound` never calls `autoVars` (no automatic fallback at all), and its
`getStyles` takes an options object (`getStyles({ part: 'hint' })`), never the
bare-string form.

## Why the intent resolver is hand-written

The default soribashi resolver hardcodes lookups of shades
`500`/`600`/`700`/`800`/`foreground` on every family the intent vocabulary
names. The TUI palette is deliberately one canonical value per hue with no ramp
(that is what mr-board's palette *is*, lifted from Tokyo Day/Night). Inventing
ramp shades would be nine tenths of a new palette and would stop being
mr-board's colours. So derivation happens in CSS instead: the base colour is the
family's single `500`, and hover is a `color-mix` wash of it at 14% — the exact
weight mr-board already uses for its one accent-tinted hover surface.

`background: "transparent"` for every intent/variant is deliberate: the TUI look
colours by border and text on an unfilled surface, and nothing in mr-board
paints a filled intent-coloured control. Variants differ only in border and wash
treatment, which lives in recipe CSS where it can be expressed per part, so
`variant` does not change what the resolver returns. `muted` is the one intent
whose family has no `500` and resolves to `--color-gray-muted`.

## Markdown at a call site that was never `.tui-md`

mr-board's ReviewModal wrapped `<Markdown>` in `<div className="tui-md">`, so
adopting the recipe there is a straight swap. CommentsDrawer is different: it
renders comment bodies inside `.tui-cd-note-body`, a separate board-owned prose
block that never carried `.tui-md`. Adopting the recipe as-is there is *not* a
no-op — `.root`'s own font/size/line-height sit directly on the wrapper element,
which beats an ancestor's inherited font regardless of layer ordering, so
comment bodies would silently pick up `.tui-md` typography they never had.

The escape hatch is the Styles API's `unstyled` prop, which suppresses `.root`'s
CSS-module class entirely while still stamping `data-part="markdown"` (that is
hand-stamped in the render body, not part of `getStyles`'s class resolution).
`unstyled` is the choice that preserves parity.

## Adoption rules that survive in mr-board's stylesheet

These are rules mr-board must keep (or rewrite) rather than delete when a recipe
absorbs the class they name — each one fails silently if dropped:

- `.tui-modal-title` / `.tui-modal-x` — the mobile drawer head and the comments
  drawer head render their own copies inside a SideDrawer's `children`. Those
  are not Modal slots.
- `.tui-review-body .tui-md { max-width: 820px; … }` — an ancestor-scoped
  reading-measure cap, not part of `.tui-md`'s typography. Rewrite onto
  `.tui-review-body [data-part="markdown"]`.
- The left overlay's `display: none` plus its `@media (max-width: 720px)`
  unhide — a board layout decision (the left drawer *is* the burger menu), not a
  property of "a left drawer". Rewrite onto
  `[data-part="sidedrawer-overlay"][data-side="left"]`.
- `.tui-menu-noting .tui-menu-label` — ancestor-scoped on an absorbed class.
  Rewrite onto `.tui-menu-noting [data-part="contextmenu-label"]`.
- Every ancestor-scoped layout rule (`.tui-controls-header .tui-seg button`,
  `.tui-drawer-controls .tui-seg`, `.tui-selbar-actions .tui-copy`,
  `.tui-drawer .tui-sidebar`, `.tui-slack-posted svg`,
  `.tui-refresh.spinning svg`) — rewrite onto the recipe's `data-part`.

All of these keep winning without `!important`: mr-board's stylesheet is
unlayered, and every recipe rule sits inside `@layer soribashi.recipes`.

## Deliberate departures from a verbatim port

Recorded because a reader comparing against mr-board's stylesheet would
otherwise read them as drift:

- **Chip** unifies `.tui-review` and `.tui-flag` into one box. `.tui-flag`'s
  `line-height: 1.5` existed only to claw back the vertical box its missing
  padding cost it, so the unified chip takes `.tui-review`'s `padding: 1px 6px`.
- **Chip** gains a `prefers-reduced-motion` escape for its pulse; mr-board's
  runs forever.
- **Chip**'s hover is the intent-tinted `--chip-hover` wash rather than a flat
  `var(--card)`, which stays as the fallback.
- **Icon**'s `flex-shrink: 0` is generalised from `.tui-review svg` to every
  icon.
- **Segmented**, **ContextMenu.Item** and **Chip**'s button form add an explicit
  `type="button"`; mr-board's never set one, so they defaulted to `submit`.
- **ContextMenu.Separator** adds `role="separator"`, valid owned content for
  `role="menu"`.
- **SideDrawer** carries no `aria-modal` — only mr-board's Modal has it, and
  adding it would change how a screen reader treats the rest of the page.
- **Modal**'s close button gets no `font: inherit`; mr-board's never had one, so
  it renders in the browser's default button font, and adding it would visibly
  change SettingsModal's literal "✕".
- **Segmented**'s `.option` gets no `font` reset either, preserving the board's
  own inconsistency with `.tui-review-open`.
- **SideDrawer** leaves the left overlay's `justify-content` unset rather than
  writing `flex-start`: the board never declares it, and the parity constraint
  is computed styles, not just pixels.
- **CopyButton** has no `gap` between icon and label — mr-board relies on
  `.tui-selbar-actions .tui-copy`'s ancestor-scoped gap for its one labelled
  call site, and the omission is preserved.

## `xxs` / `xxl` scale key names

SORI-6 (`getSize()` mis-reading digit-leading keys) is fixed upstream, so
`2xs`/`2xl` would now work. The names stay as they are: renaming churns every
emitted CSS variable and every recipe reference for zero behavioural gain.
