> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `@mattstack/tui-kit` — the mattstack TUI look (Tokyo Day/Night theme + mr-board's ui/ layer) as a soribashi-conventions library — and adopt it in mr-board at pixel-identical parity.

**Architecture:** New repo at `~/Documents/GitHub/tui-kit` (bun workspace root, source-consumed package), depending on unpublished soribashi via verified `file:` + overrides wiring. Milestone A builds the kit (theme with verbatim token values, 12 recipes + hooks, soribashi's mechanical gates, Vite workshop). Milestone B adopts it in an mr-board worktree, gated by the existing capture harness at zero pixel tolerance.

**Tech Stack:** Bun 1.3.x, React 19 (peer), soribashi (core/factory/theme/codegen via file: siblings, pinned commit), CSS Modules, vitest browser mode + playwright provider + vitest-browser-react (kit), bun test + Playwright capture harness (mr-board).

**Spec:** `docs/superpowers/specs/2026-08-19-tui-kit-design.md` (in mr-board; Task 1 copies it into tui-kit). The spec is the binding authority; where this plan and the spec disagree, the spec wins.

## Global Constraints

- All kit tasks run in `~/Documents/GitHub/tui-kit`; all adoption tasks (Milestone B) run in the worktree `~/Documents/GitHub/mr-board-wt-tui-adopt`. NEVER modify `~/Documents/GitHub/mr-board` (main checkout) or `~/Documents/GitHub/soribashi`.
- **Dogfood rule (spec Decision 5):** every soribashi bug, gap, or paper cut you hit becomes a Linear ticket on the `soribashi` team AT THE MOMENT OF ENCOUNTER — repro + workaround taken. Implementers report the friction in their task report; the controller files the ticket. Never silently work around the framework.
- Token VALUES are carried verbatim from mr-board's `src/style.css` (hex/rgba strings unchanged) — parity is by construction; never "improve" a color.
- Every recipe: soribashi's four-file layout, `export const recipeCategory = N as const`, hand-stamped `data-part` on each addressable slot (tui-kit convention), NEVER hand-emit `data-variant`/`data-intent`/`data-size` (builders own those).
- Kit CSS obeys the no-hardcoded-values gate: every color/length through `var(--...)` except the allowlist (`0`, `1px`, `2px`, `100%`, unitless, time values); sanctioned outlets for stragglers: a token, a `var()` with literal fallback (comment required), or an allowlist entry (comment required).
- Kit commit messages and mr-board commit messages end with:
  `Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>`
- Kit gates (run green before every kit commit): `bun run typecheck`, `bun run test` (vitest), `bun run gates` (no-hardcoded-values + token-existence + codegen drift). Adoption gates (before every adoption commit): `bun run typecheck && bun test && bun run capture && bun run capture:compare` (zero diffs unless the task says otherwise).
- Adoption refresh rule: after ANY kit edit, refresh the worktree with argument-less `bun install --force` (NEVER `bun install --force <pkg>` — that is add-semantics and fetches from npm) before running captures.

- [ ] **Step 4: Write src/intent-resolver.ts** — the default resolver requires 500–800 ramps the TUI palette doesn't have; per spec, a custom resolver built on color-mix:

```ts
import type { IntentResolver } from "@soribashi/theme";

/** Family per intent word (spec's mapping table). */
const FAMILY: Record<string, string> = {
  accent: "blue", ok: "green", warn: "amber", bad: "red",
  cyan: "cyan", purple: "purple", muted: "gray",
};

/** TUI components color via currentColor borders + text color, not filled
    ramps, so the resolver derives hover/wash from the single canonical value
    with color-mix instead of ramp shades. `muted` maps to the gray family's
    `muted` slot rather than a 500. */
export const tuiIntentResolver: IntentResolver = ({ intent, variant }) => {
  const fam = FAMILY[intent] ?? "blue";
  const base = intent === "muted" ? `var(--color-gray-muted)` : `var(--color-${fam}-500)`;
  void variant; // TUI variants share one coloring model; variant differences live in recipe CSS
  return {
    bg: "transparent",
    color: base,
    border: base,
    hover: `color-mix(in srgb, ${base} 14%, transparent)`,
  };
};
```
